# Standalone acceptance matrix — v0.2.0

The source document is the product reference. Its embedded D1 kickoff and deployment instructions are not treated as additional user instructions. This release completes the standalone operating workflows; it does not connect to Bidlark, another scheduler's live database, procurement services, live payment or email accounts. SMTP and Stripe adapters are implemented and locally contract-tested.

## Interpretation and boundaries

- Daily-report time is the standalone timecard source. Approving or voiding its report controls whether the time contributes. A report correction references a rejected or voided original; it does not edit an approved source in place.
- A field-change approval records authorization and evidence. Quantity/estimate edits and schedule revisions remain separate explicit actions. A substitution approval does not assert receipt of the replacement.
- Dependency calculations are finish-to-start working-calendar scenarios. They do not implement every scheduling product's constraint/link type. Person-level cross-project conflicts are visible only for projects the user may access; no unauthorized project names are disclosed.
- Finance is a project source-entry register in USD, not a payroll, accounting or payment system. Payroll rates are not stored. Approved revenue and contract values are user-provided source facts; forecasts are labeled estimates. Financial projections require complete activity allocation and verified progress.
- Setup JSON is the open interchange format for externally prepared schedules/estimates. Live Bidlark/Gantt/material module adapters remain the requested later integration.
- Scheduled email delivery is implemented, including all nine layouts for internal recipients. External recipients receive restricted single-project publications, never portfolio attachments. SMTP acceptance does not prove inbox delivery; delivery is at-least-once after an ambiguous network failure.
- The default standalone MIT installation includes all dashboard features. Optional Stripe mode supports hosted subscription checkout, a customer portal, signed webhook reconciliation and tenant entitlements. It supplements role/project authorization. Real provider configuration and a Stripe sandbox acceptance run remain necessary before collecting money; no live payments were attempted.
- OIDC is implemented and protocol-tested, but a specific customer's identity provider still needs its own issuer, client credentials and explicit identity mappings. No third-party identity tenant was provisioned or modified.
- A measured staging run is not an unlimited-capacity guarantee or independent penetration test. Use the deployment guide for host sizing, TLS, persistent volumes and recovery operations.
